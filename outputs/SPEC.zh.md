# Outputs：一个渠道的契约

`outputs/` 存放关于*去处*的一切：某个渠道该怎么写、当前发布了什么、以及文案本身。它不含事实。事实住在 `wiki/` 里，通过 slug 被拉取。

本文件就是契约。任何 `outputs/<channel>/SPEC.md` 都必须遵守它。

## 目录形状

```
outputs/<channel>/
  SPEC.md      规则（本契约要求的章节，逐项填好）
  state.md     当前生效的是什么 + 版本表
  drafts/      每次发布一个子目录：drafts/2026-11/
```

`_template/` 是新增渠道时要复制的骨架。不要就地编辑它。

## 渠道 SPEC 的必需章节

| # | 章节 | 必须回答 |
|---|---|---|
| 1 | 受众与目标 | 谁读它，他们据此做什么决定 |
| 2 | 结构 | 固定的字段顺序，一个字段一行 |
| 3 | 硬上限 | 表格：字段、平台上限、最近一次实测值 |
| 4 | 裁剪优先级 | 有序清单：超限时先砍什么、再砍什么、最后砍什么 |
| 5 | 事实映射 | 字段 → wiki slug。这张表正是规格不含事实的原因 |
| 6 | 命名 | 渠道会原样展示的标题、标签与译名 |
| 7 | 禁写项 | 你在此永不做的断言，每条附一行理由 |
| 8 | 验收清单 | 发布前逐项可勾选的检查 |
| 9 | 发布流程 | 草稿如何变成正式版，以及要记录什么 |

缺少第 3、4、5、7 节的"规格"只是风格指南，不是规格。

## SPEC 不得包含什么

- **事实。** 不要日期、年限、计数、人名。它们会过期；slug 不会。
- **你不打算公开的个人实测值。** "Headline 上限 220"是公开信息；"我上次写到 75 个字符"不是——记在 `state.md` 里。
- **草稿文案。** 文案属于 `drafts/`；引用段落的规格必然与线上版本漂移。

## state.md 的形状

```
## Current
- 版本、日期、发布在哪、谁确认

## Known deviations
- 现在哪里不对，以及是否会修

## Versions
| 版本 | 日期 | 变更 |

## Next action
- 下一步唯一要做的事
```

## 发布流程

1. 读 `outputs/<channel>/SPEC.md` 及其事实映射里的 wiki 页。
2. 把草稿渲染进 `outputs/<channel>/drafts/<YYYY-MM>/`。
3. 机械地检查上限（字符数必须*实测*，不能估算）。
4. 走一遍验收清单；改草稿，不改规格。
5. 若某个事实是错的，停下：先修 `wiki/`（铁律 4），再重新渲染。
6. 更新 `state.md`（版本、日期、偏差），并向 `wiki/log.md` 追加记录。

## 跨渠道一致性

同一个事实被渲染到多个渠道时：

- 事实只来自一个 wiki 页；两个渠道对不上时，默认草稿更旧的那个渠道是错的。
- 改一个事实意味着重新渲染引用它的**每一个**渠道。受影响渠道超过两个时，在 wiki 页的 "rendered by" 注记里列出它们。
- 语言变体是同一份规格的不同草稿，不是不同的规格。
